# Architecture and layers

This analysis describes the source at HEAD `e3dd2e1`. The repository contains two runnable process forms. The HTTP key-value service is one binary (`go run ./http-service`); the TCP Reactor demo is another (`go run ./cmd/server`) with a protocol client (`go run ./cmd/cli`). They do not call each other; dependency direction is toward interface seams.

For term-by-term definitions and source anchors, see the [glossary](/glossary). The reverse link is on that page.

## Abstract layers

1. **Application lifecycle** turns command-line and YAML input into one runnable service, then owns signal-to-drain behavior. The HTTP binary wires `Service(MemoryStore)` and an `http.Server` at `http-service/main.go:40`; the TCP binary binds Viper keys and flags to `ServerOptions`, starts a Reactor, and waits for signals at `cmd/server/main.go:15`; the protocol CLI chooses a plain or resilient client and runs request/watch lifecycles at `cmd/cli/client.go:39`. The protocol server schema is `config.example.yml:4` and its flag binding is `cmd/server/main.go:86`; the HTTP flags are defined at `http-service/main.go:30`.
2. **Transport access** owns bytes entering and leaving the process. The Reactor accept loop passes a connection to a worker at `pkg/reactor/reactor.go:92`; worker queues dispatch it and a connection goroutine drives each pipeline at `pkg/reactor/worker.go:206`. The HTTP process instead accepts a request inside `net/http` and maps routes and status codes at `http-service/handler.go:14`.
3. **Message pipeline** propagates connection events through ordered handlers. The interface chain is `pkg/handler/handler.go:52`; the linked pipeline inserts head/tail nodes and dispatches inbound from head to tail at `internal/handler/linked_pipeline.go:90`, while `NodeContext` skips the current node on inbound and walks backward on outbound at `internal/handler/node_context.go:103`. Reactor's default error listener and tail close connection on unhandled errors at `internal/handler/event_listener.go:17` and `internal/handler/tail_header.go:25`.
4. **Wire protocol** is the TCP-specific stateful contract. `FrameCodec` decodes and encodes frames at `pkg/proto/protocol.go:765`; `ProtocolHandler` performs HELLO negotiation, request handling, subscription tracking, replay and publish at `pkg/proto/protocol.go:76` and `pkg/proto/protocol.go:285`. Its client counterpart maintains pending calls, keepalive and graceful close at `pkg/proto/client.go:266`; the resilient client keeps a session token and replay cursors across reconnects at `pkg/proto/resilient.go:56`.
5. **Business semantics** are split by process form. The HTTP service validates keys and exactly-one-JSON values and maps missing/invalid data to business errors at `http-service/service.go:41`; the TCP demo leaves action execution to a `RequestHandler` callback configured at `cmd/server/demo/demo.go:27`. HTTP storage is intentionally only a map behind a seam at `http-service/store.go:19`; no Redis, MySQL, remote database or dedicated persistence file participates in production.
6. **Distribution policy** selects a worker for each accepted connection. `WorkerGroup` defaults to an adaptive balancer at `pkg/reactor/worker.go:52`; the adaptive algorithm reads a live load value once per backend and resolves ties randomly at `internal/balancer/adaptive.go:42`. Round-robin, random, IP-hashing, least-connections and weighted alternatives implement the same generic interface at `pkg/balancer.go:19`; `Worker.Load()` supplies adaptive input at `pkg/reactor/worker.go:263`.
7. **Runtime resource control** supplies concurrency primitives, execution futures and buffer ownership. The async executor routes tasks and futures through unbuffered channels at `internal/executor/async_executor.go:85`; futures expose done/cancel/timeout resolution at `internal/executor/async_future.go:33`; protocol payload pools recycle size-classed buffers at `pkg/proto/pool.go:133`; graceful signal handling and generic option/contract packages are `pkg/utils/graceful.go:45`, `pkg/options.go:8` and `pkg/balancer.go:19`.

## Why these are separate layers

1. **Lifecycle is separated from accept/read work because two independent process forms need different shutdown contracts.** The HTTP process waits on a signal and calls `http.Server.Shutdown` with a configurable deadline at `http-service/main.go:64`; the Reactor closes its listener, drains active connections, force-closes survivors, stops worker loops and reports a leak if handlers remain at `pkg/reactor/reactor.go:177`. Reusing one lifecycle type would couple signal policy to those different drain stages.
2. **Transport access is separated from pipeline because the two forms already share no connection abstraction.** Reactor owns `net.Listener`, accept retry and worker dispatch at `pkg/reactor/reactor.go:105`; HTTP handlers receive an `*http.Request` and write through `http.ResponseWriter` at `http-service/handler.go:71`. A single transport layer would have to abstract both without reducing either code path.
3. **Pipeline is separated from protocol because Reactor accepts pluggable initializers and handlers rather than hard-coding protocol semantics.** `NewReactor` receives `handler.PipelineInitializer` at `pkg/reactor/reactor.go:42`; `echoInitializer` installs only frame codec plus protocol handler at `cmd/server/demo/demo.go:33`; inbound and outbound propagation direction is implemented independently at `internal/handler/node_context.go:103`. This is a real extension seam, not directory decoration.
4. **Wire protocol is split into codec, server state and client resilience because the state machines own incompatible memories.** Codec boundaries and stream assembly are isolated at `pkg/proto/protocol.go:765`; server sessions, topic sequences and a byte-budgeted replay cache are protected by one RWMutex at `pkg/proto/protocol.go:84`; pending response channels and keepalive state live in the client at `pkg/proto/client.go:85`; reconnect tokens and cursors live in `ResilientClient` at `pkg/proto/resilient.go:56`. Combining them would put per-process and per-connection ownership in one object.
5. **Business semantics are separated from protocol/HTTP framing because the two binaries define validity differently.** HTTP validates printable ASCII keys, one JSON value and a configured size limit at `http-service/service.go:41`; the TCP demo accepts an arbitrary action callback and only packages JSON bytes at `cmd/server/demo/demo.go:27`. A shared business layer would invent rules neither process owns.
6. **Distribution policy is separate because scheduling depends on live worker counters and can be injected without changing dispatch.** `WorkerGroup` defaults to adaptive selection at `pkg/reactor/worker.go:66`, dispatch calls `balancer.Next` at `pkg/reactor/worker.go:91`, and `Worker` reports its own active-connection count at `pkg/reactor/worker.go:263`. Alternative balancers register/unregister through the same generic contract at `internal/balancer/adaptive.go:85`.
7. **Resource control is separate because channel/future execution and wire-buffer reuse are cross-cutting concerns with explicit ownership rules.** The executor drops tasks after context cancellation and runs tasks/futures from a shared worker loop at `internal/executor/async_executor.go:71`; payload pools zero and recycle buffers to prevent stale-data reuse at `pkg/proto/pool.go:157`. These policies are useful to protocol/runtime code but are not protocol semantics themselves.

## Unreasonable classification

- `pkg/balancer.go` is a generic contract file whose only concrete implementation is under `internal/balancer`; the `Balancer` interface is exported at `pkg/balancer.go:19` and consumed by the reactor worker (`pkg/reactor/worker.go:91`), so it stays public. The executor contract (`Executor`/`Future`/`Action`/`ActionWithReturn`) has no production caller — its only public consumer, `handler.ExecutorHandler`, was a dormant zero-implementation interface (asserted but never dispatched) and has been removed — so the contract now lives with its implementation at `internal/executor/contract.go:20`, concrete code at `internal/executor/async_executor.go:38`.
- `internal/handler/head_handler.go` imports and implements `pkg/handler` interfaces at `internal/handler/head_handler.go:6`, while `pkg/reactor` also imports the `internal` pipeline. The public Reactor API therefore depends on a private implementation package; moving the concrete pipeline to `pkg/handler` (or exposing a narrower injection contract) would align the access boundary.
- `cmd/server/main.go` now holds only process configuration wiring; the protocol demo action and its pipeline initializer live in the `cmd/server/demo` package (`cmd/server/demo/demo.go:27`, `cmd/server/demo/demo.go:33`). `cmd/cli/client.go` still mixes parsing, execution and watch UX.
